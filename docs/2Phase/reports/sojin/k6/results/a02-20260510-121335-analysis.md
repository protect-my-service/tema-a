## 4. CPU가 두 번 튄 이유

방어팀 모니터링에서 12:13대 / 12:15대 두 번의 CPU 스파이크가 관측됨.
이 분포와 정확히 매칭되며 다음 3단계 흐름으로 해석됩니다.

1. **12:13대 — 1차 피크**
   - RPS 100 진입 직후, postOrder가 1,890건 통과.
   - 모든 요청이 동일 row(P1)에 `SELECT ... FOR UPDATE`를 걸어 직렬화.
   - 평균 134.6ms / max 663ms — 락 큐가 차오르며 응답 길어짐.

2. **12:14대 — 골 (서버가 막힘)**
   - cart 단계에서 timeout(status=0) **5,775건**, 403 **121건**.
   - 트래픽이 서버까지 도달 못함 → CPU도 동시에 떨어짐.
   - 방어팀이 일시적으로 **레이트리밋/방어 정책**을 걸었거나, ngrok 무료 티어의 RPS 한도에 걸렸을 가능성.

3. **12:15대 — 2차 피크 (더 강함)**
   - 차단이 풀리며 다시 RPS 100 진입, postOrder 1,986건 통과.
   - **max latency 929ms** (1차 663ms 대비 +40%).
   - 방어 정책 해제 직후 큐잉됐던 요청까지 한꺼번에 들어가 락이 더 깊게 걸림 → CPU가 1차보다 더 강하게 튐.

즉 **공격 → 방어 대응 → 재공격**이 한 번의 k6 실행 안에서 자연스럽게 일어났고, 이게 두 번의 CPU 스파이크의 원인입니다.

## 7. 시사점 / 다음 액션

1. **방어팀이 레이트리밋류 대응을 가지고 있음** — 12:14에 정확히 트래픽이 차단됐다 풀린 흔적. 어떤 임계로 동작하는지 추가 실험으로 좁힐 가치 있음.
2. **2차 피크가 더 강하게 튐** — 차단 해제 직후가 가장 위험. ramping-arrival-rate(점진 증가)로 길게 끌면 차단/해제 사이클이 반복되며 더 두드러질 가능성.
3. **5xx는 거의 안나옴** — 단순 RPS 100 / 3분으로는 락 timeout까지 밀어붙이기 어려움. ATK-A03(RPS 50→100→150→200 단계 상승)으로 풀 고갈까지 이어지는지 확인 필요.
4. **카트 단계 status=0이 7,436건** — 7할 가까이 응답을 못받음. 다음 회차에는 ngrok 대신 직접 IP로 붙거나, 더 안정적인 터널을 쓰는 게 좋겠음.
